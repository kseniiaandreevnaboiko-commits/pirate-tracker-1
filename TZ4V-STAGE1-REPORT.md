# ТЗ № 4В, этап 1 — отчёт проверки и план перехода

Дата проверки: 15 октября 2026 года. Ветка:
`feature/tz4b-secure-economy`, базовый коммит этапа: `8bf717b`.

## Границы проверки

Использовались только локальные Firebase Auth, Firestore и Hosting Emulator с
project ID `demo-pirate-auth` и искусственными данными. Production-запись,
deploy, push, удаление `/trackerApps/main` и создание реальных учеников не
выполнялись.

Встроенный браузер в текущей среде не предоставил ни одного доступного браузера.
Поэтому визуальные пункты не считаются пройденными и вынесены в обязательный
ручной чек-лист ниже. HTTP-доступность локального приложения проверена ранее,
но она не заменяет визуальную проверку.

## Автоматические проверки

- 23 из 23 тестов прошли в Auth/Firestore Emulator.
- Сквозной интеграционный тест проверил начисление, идемпотентность, покупку,
  повторное подтверждение, ручное достижение, автоматические достижения и
  сохранение истории при смене сезона.
- Добавлена отдельная проверка, что анонимный ученик не может подтвердить
  покупку, создать достижение, прочитать `/trackerApps/main` или назначить себе
  роль учителя.
- При `lifetimeEarned = 350` функция рангов возвращает «Адмирал». Покупка на
  100 ФК оставляет `balance = 250`, `lifetimeEarned = 350` и тот же ранг.

## Соответствие утверждённой логике сезонов

Реализация соответствует правилу «один сезон = полный курс из 30 занятий»:

1. В коде нет автоматического перехода по номеру занятия.
2. Чемпионаты 10/20/30 не связаны с `startNewSeason`.
3. `balance` и `lifetimeEarned` меняются непрерывно до явной команды.
4. Завершение занятия не вызывает обнуление.
5. Новый сезон доступен только отдельной учительской кнопкой.
6. Перед выполнением показывается предупреждение с подтверждением.
7. Операция архивирует итоговые `balance`, `lifetimeEarned` и ранг.
8. Транзакции, покупки и достижения не удаляются.

Новый сезон в ходе этой проверки не запускался вручную. Его транзакционное
поведение покрыто автоматическим тестом на искусственных данных.

## Найденные ограничения и риски

1. Защищённый режим сейчас намеренно включается только на localhost с
   `?emulator=1`; `secure-auth.js` содержит demo project ID и всегда подключает
   эмуляторы. Обычная опубликованная версия продолжит использовать старую
   анонимную синхронизацию `/trackerApps/main`. Это блокирует production-запуск.
2. Мигратор намеренно запрещает любой не-localhost хост и project ID без
   `demo-`. Для production нужен отдельный проверяемый dry-run/execute сценарий.
3. Визуальная и адаптивная проверка не завершена из-за отсутствия браузера.
4. Нужно подтвердить фактический источник GitHub Pages и добавить домен Pages в
   Authorized domains Firebase Authentication.
5. Между публикацией новых Rules и новой страницы возможен короткий период
   несовместимости. Нужна согласованная пауза или maintenance-страница.
6. Официальный managed export Firestore требует billing/Blaze. На Spark нужен
   отдельно проверенный локальный read-only JSON backup либо временный переход
   на Blaze для официального экспорта.

## План production-перехода — не выполнять без отдельного подтверждения

### 1. Подготовить production-сборку

1. Убрать жёсткую привязку защищённого режима к localhost.
2. Вынести production Firebase config отдельно от demo config; в production не
   вызывать `connectAuthEmulator` и `connectFirestoreEmulator`.
3. Проверить, что legacy `firebase-sync.js` больше не загружается в защищённом
   production-режиме.
4. Создать staging-конфигурацию или отдельный Firebase demo/staging project и
   повторить весь ручной чек-лист.
5. Зафиксировать кандидата релиза тегом; текущий production baseline —
   `b86982c9649e47c5c20b358c4b69bb24b1252913`.

### 2. Сделать и проверить резервные копии

1. Объявить короткое окно обслуживания и закрыть все вкладки старого приложения,
   чтобы `/trackerApps/main` не менялся во время копирования.
2. На Spark выполнить будущий локальный read-only backup-скрипт: прочитать
   `/trackerApps/main`, сохранить исходный документ и `state` в два JSON-файла,
   записать время, project ID, UID читателя, размер и SHA-256. Не хранить backup
   в Git.
3. Дополнительно сохранить локальную копию `pirateTracker` с доверенного
   учительского устройства и сравнить её с Firestore.
4. Экспортировать Firebase Auth командой `firebase auth:export` в защищённый
   каталог; файл содержит чувствительные хэши и соли.
5. Если разрешён временный Blaze, предпочесть официальный managed export всего
   Firestore в отдельный Cloud Storage bucket.
6. Проверить backup парсингом JSON, контрольной суммой, количеством классов,
   учеников, транзакций, товаров, заявок и достижений; импортировать копию в
   чистый Emulator и сравнить агрегаты и ID.
7. Хранить минимум две зашифрованные копии в разных местах.

### 3. Подготовить учительскую учётную запись

1. В Firebase Console открыть Authentication → Users и найти уже созданный
   email учителя.
2. Скопировать его UID; не создавать новый аккаунт и не менять пароль.
3. До включения новых Rules административно создать
   `/authorizedTeachers/{uid}` с `{ active: true }`.
4. Перепроверить точное совпадение UID Auth и ID документа, затем выполнить
   тестовый вход. Email сам по себе ролью не является.

### 4. Выполнить production dry-run миграции

1. Создать отдельный production-мигратор с режимами `--dry-run` и `--execute`,
   явным project ID, подтверждением контрольной суммы backup и запретом удаления.
2. На dry-run сформировать план записей и список расхождений без записи.
3. Остановиться при неизвестных ID, отрицательных балансах, дубликатах,
   неподтверждённых покупках или несовпадении итогов.
4. После письменного согласования запустить `--execute` один раз. Скрипт должен
   быть идемпотентным и не трогать `/trackerApps/main`.
5. Повторно выгрузить новые коллекции и сравнить «до/после» по каждому классу.

### 5. Правила и GitHub Pages

1. Ещё раз выполнить Emulator tests из точного release commit.
2. Проверить Rules в Firebase Rules Playground для учителя, своего ученика,
   чужого ученика и непривязанного anonymous UID.
3. В окно обслуживания опубликовать Rules отдельной командой
   `firebase deploy --only firestore --project <production-id>` и сразу провести
   отрицательные проверки.
4. Добавить домен GitHub Pages в Firebase Authentication Authorized domains.
5. Создать PR release-ветки в publishing branch. Проверить diff: никаких backup,
   паролей, service-account файлов и тестовых данных.
6. GitHub Pages публиковать из явно настроенной ветки/root либо защищённым Pages
   workflow. Зафиксировать commit SHA и URL deployment.
7. После публикации очистить cache только тестового профиля и пройти smoke test:
   вход учителя, чтение класса, тестовое начисление/отмена, вход тестового
   ученика, заявка/отклонение, достижения и рейтинг.

### 6. Откат

1. Не удалять и не изменять `/trackerApps/main` минимум до завершения полного
   курса проверки и отдельного решения об архивировании.
2. При проблеме прекратить работу пользователей и сохранить диагностический
   снимок новых коллекций.
3. Вернуть GitHub Pages на зафиксированный предыдущий commit/tag.
4. Вернуть предыдущие Rules, разрешающие старому приложению доступ только к
   `/trackerApps/main`, из проверенного release-артефакта.
5. Новые коллекции при аварийном откате не удалять: старая версия их игнорирует.
6. Проверить старый вход и совпадение legacy-документа с backup.
7. Если повреждены данные, восстанавливать только после сравнения текущего
   состояния, backup и журнала миграции; отменённый import сам изменения не
   откатывает.

## Заключение

Серверная модель, миграция на искусственных данных, экономика и Rules готовы к
следующей подготовительной итерации. К production-запуску проект пока не готов:
обязательны production-конфигурация защищённого клиента, отдельный безопасный
production-мигратор, проверенный backup и полный ручной визуальный чек-лист.
